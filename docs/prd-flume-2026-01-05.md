## Executive Summary

Flume is the "Corporate Charter" for the 33GOD Agentic Pipeline - an implementation-agnostic protocol that defines structural hierarchy, communication interfaces, and role definitions for multi-agent orchestration. It rejects standard AI terminology (chains, nodes, tools) in favor of strictly anthropomorphic roles: Employees, Managers, Contributors, and Directors.

Yi is the opinionated adapter layer that wraps diverse agent frameworks (Letta, Claude, Agno) and forces them to wear the Flume corporate uniform, enforcing 33GOD conventions like shared memory strategies, standardized onboarding, HR-managed recruitment, and Bloodbank event emission.

---

## Product Goals

### Business Objectives

1. **Unified Multi-Agent Protocol**: Create a framework-agnostic protocol that enables any AI agent to participate in coordinated workflows using a consistent interface
2. **Corporate Anthropomorphization**: Establish a scalable pattern for complex work using corporate hierarchy metaphors that map naturally to delegation and reporting structures
3. **Full Observability**: Every state change emits events to Bloodbank (RabbitMQ), enabling complete traceability of agent actions, delegations, and results
4. **Framework Flexibility**: Support multiple LLM backends (Claude, Letta, future frameworks) through Yi adapters without changing the core protocol

### Success Metrics

| Metric | Target | Measurement |

| E2E Task Completion | 95%+ tasks complete successfully | Bloodbank event analysis |

| State Machine Compliance | 0 invalid transitions | Runtime validation |

## Functional Requirements

Functional Requirements (FRs) define **what** the system does - specific features and behaviors.

Each requirement includes:
- **ID**: Unique identifier (FR-001, FR-002, etc.)
- **Priority**: Must Have / Should Have / Could Have / Won't Have (MoSCoW)
- **Description**: What the system should do
- **Acceptance Criteria**: How to verify it's complete

---

### FR-001: Corporate Hierarchy Type System

**Priority:** Must Have

**Description:**
Define TypeScript interfaces for the corporate hierarchy: Employee (base), Contributor (leaf/IC), Delegator (has subordinates), Manager (can delegate AND execute), and Director (pure orchestrator).

**Acceptance Criteria:**
- [x] Employee interface with id, name, role, state, teamId, skills, salary, reportStatus()
- [x] Contributor interface extends Employee with canHandle() and execute()
- [x] Delegator interface with subordinates[], recruit(), release(), delegate()
- [x] Manager interface combines Contributor + Delegator
- [x] Director interface combines Employee + Delegator (no execute)
- [x] SelectionStrategy interface for delegation routing

**Dependencies:** None

**Status:** COMPLETE (flume-core/src/types/employee.ts)

## Non-Functional Requirements

Non-Functional Requirements (NFRs) define **how** the system performs - quality attributes and constraints.

---

### NFR-001: Performance - Task Execution Latency

**Priority:** Must Have

**Description:**
Task execution overhead from Flume/Yi layer should be minimal, not including LLM inference time.

**Acceptance Criteria:**
- [ ] Framework overhead < 50ms per task (excluding LLM calls)
- [ ] Event emission < 10ms per event
- [ ] Selection strategy execution < 100ms for up to 50 candidates

**Rationale:**
Framework overhead should be negligible compared to LLM inference time.

---

### NFR-002: Reliability - Event Delivery

**Priority:** Must Have

**Description:**
All Bloodbank events must be delivered reliably with at-least-once semantics.

**Acceptance Criteria:**
- [ ] Event queuing when RabbitMQ unavailable
- [ ] Automatic reconnection with exponential backoff
- [ ] Persistent messages (survive broker restart)
- [ ] Dead letter queue for failed events

**Rationale:**
Event loss breaks correlation chain traceability, defeating observability goals.

---

### NFR-003: Scalability - Concurrent Agents

**Priority:** Should Have

**Description:**
Support concurrent agent execution within a single Yi process.

**Acceptance Criteria:**
- [ ] Support 50+ concurrent agents per process
- [ ] Thread-safe state management
- [ ] No blocking on delegation chains

**Rationale:**
Production deployments need multiple agents handling tasks simultaneously.

---

### NFR-004: Maintainability - Type Safety

**Priority:** Must Have

**Description:**
Full TypeScript strict mode compliance with no `any` types in core interfaces.

**Acceptance Criteria:**
- [ ] tsconfig strict mode enabled
- [ ] No `any` in flume-core types
- [ ] Minimal `unknown` with proper type guards
- [ ] All public APIs have JSDoc documentation

**Rationale:**
Type safety prevents runtime errors and enables IDE support for adopters.

---

### NFR-005: Testability - Unit Test Coverage

**Priority:** Should Have

**Description:**
Core logic should have comprehensive unit test coverage.

**Acceptance Criteria:**
- [ ] 80%+ line coverage for flume-core
- [ ] 70%+ line coverage for yi-adapter
- [ ] Integration tests for each Yi adapter
- [ ] Walking skeleton E2E tests pass

**Rationale:**
Protocol changes must not break existing implementations.

---

### NFR-006: Compatibility - Node.js Version

**Priority:** Must Have

**Description:**
Support modern Node.js versions with ESM modules.

**Acceptance Criteria:**
- [x] Node.js 20+ required
- [x] ESM module format
- [x] TypeScript 5.3+ compatibility

**Rationale:**
ESM is the future of Node.js, and Node 20 is current LTS.

## User Personas

### Framework Developer
Developers building agentic systems using Flume/Yi. They implement custom adapters, configure hierarchies, and integrate with their existing LLM infrastructure.

### Orchestrator
Systems or humans that submit tasks to a Flume hierarchy and consume results. They care about task completion, not implementation details.

### Operator
DevOps/SRE responsible for running Flume/Yi in production. They need observability, health checks, and operational controls.

## User Flows

### Flow 1: Task Delegation Chain

1. Orchestrator submits TaskPayload to Director
2. Director selects appropriate Manager via SelectionStrategy
3. Manager either executes directly or delegates to Contributor
4. Contributor executes task, returns WorkResult
5. Results bubble up through chain
6. Each step emits Bloodbank events for traceability

### Flow 2: Dynamic Agent Recruitment

1. Manager needs specialist skills not on team
2. Manager submits RecruitmentRequest to HR
3. HR finds appropriate AgentFactory
4. Factory creates raw agent
5. Onboarding injects team context
6. Ready agent joins Manager's subordinates
7. Manager delegates task to new recruit

---

## Assumptions

1. RabbitMQ is available in the deployment environment (Bloodbank)
2. Each adapter is optional - deployments can use subset of adapters
3. Agent implementations are single-threaded (async but not parallel)
4. LLM API costs are tracked but not enforced by the framework

---

## Out of Scope

1. **LLM Training/Fine-tuning**: Flume orchestrates, doesn't train
2. **UI/Dashboard**: Observability via Bloodbank consumers, not built-in UI
3. **Multi-tenant Isolation**: Single-tenant deployment model
4. **Agent-to-Agent Direct Communication**: All communication via delegation
5. **Automatic Scaling**: Manual agent count management

---

## Open Questions

1. **Memory Strategy Standardization**: Should all adapters share a common memory interface, or is adapter-specific memory acceptable?
2. **Error Recovery Policy**: Should failed tasks auto-retry at framework level, or delegate to orchestrator?
3. **Contractor vs FTE Semantics**: How should ephemeral "contractor" agents differ from persistent agents?
