# FLUME-14 routing readiness evidence

The Bloodbank review reads the existing Hermes `gateway.sock` control protocol `identify` verb, protocol 1. It does not ask the gateway to rescan, invoke an employee, send/replay a Bloodbank command, or alter service state. The response is built by the serving gateway on this connection from its current runtime descriptor (`gateway/run_bootstrap.py`, `_identify_runtime`); the served set is published from live session authorities (`gateway/run_runtime.py`, `_publish_served_set`; `gateway/session_authorities.py`, `served_profiles`). No persisted timestamp, PID, registry declaration, or historical dispatch is accepted as a positive route. This proves current gateway profile addressability, **not** Bloodbank broker subscription, delivery, execution or activation.

A positive observation requires the handbook's fleet scope, a target equal to the selected employee ID, a uniquely claimed and resolved profile directory, a same-owner control socket, protocol-1 reply with matching request ID, matching Hermes home and runtime protocol, `state: ready`, `session-authority-v1`, and exactly one matching `{profile_id, home}` equal to that profile's resolved home. Empty served set, duplicated or conflicting entries, invalid profile, wrong target or scope fail. Missing/denied socket, incomplete evidence, malformed response and timeout remain unproven/error. Stable reason codes replace all untrusted response text; the 512 KiB reply cap and per-probe/shared-run deadlines apply. A domain-filtered invocation reads only selected employees and does not start the recipe audit. Routing readiness is separate from the registry's strict activation gate: absent grants, explicit false denies, and present invalid denies; none is written by review.
