# Cloudflare machine authentication — supplemental decision check

Accessed 2026-10-10; all below primary Cloudflare documents retrieved this run.

1. https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/ (updated 2026-10-02): service tokens are client-ID/client-secret pairs for automated callers to Access-protected applications, support individual rotation/expiry/disable/revoke; Service Auth policies are the documented path. New organizations since 2026-10-05 use strict service auth without CF_Authorization cookies, require headers each request and ignore Allow policies for service-token requests. Existing-org behavior must be inspected, not inferred. Docs also announce a new secret format; do not hard-code token lengths. Confidence: primary-documented, not tested on user account.
2. https://developers.cloudflare.com/cloudflare-one/account-limits/ (updated 2026-09-04): default Access service-token limit is 50 per account; this is NOT the same as 50 human user seats. Existing integrations consume capacity. No guarantee a limit increase is free. Confidence: primary-documented.
3. https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/ (updated 2026-06-25): service-token JWT has `sub: ""` and signed `common_name` equals service token Client ID. Human JWT's email/sub semantics do not apply to machines. Map `(iss, common_name)` after signature/audience/expiry validation to Flume's subject; do not use an empty sub for every employee or trust a client-supplied header in isolation. Confidence: primary-documented; mapping is our architecture recommendation.
4. https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/ (updated 2026-05-06): origin should verify Cf-Access-Jwt-Assertion, signature via account JWKS, expected issuer and application audience. Cloudflare supplies an example using jose. Enforce expiry and application-specific machine-principal mapping; prevent direct-origin bypass. Confidence: primary-documented, not a deployed proof.
5. https://www.cloudflare.com/sase/products/access (search excerpt only, undated): advertises a $0 free plan for teams under 50 users. This research did not inspect account entitlements or prove service-token seat billing. Do not equate the marketing user allowance with the distinct service-token limit.

Recommendation (design judgment): prefer one Cloudflare Access service token per canary employee, held by a trusted launcher with references in Flume, to avoid deploying a new IdP before the need exists. Put auth behind an adapter: Keycloak service accounts are the OSS replacement if account capacity/entitlements or portability requires it; SPIRE is for actual workload attestation. Do not deploy all three. Service tokens prove possession, not OS-level isolation between arbitrary same-user processes.

Independent cross-check: GitHub's current Terms of Service was fetched directly at https://docs.github.com/en/site-policy/github-terms/github-terms-of-service (effective 2026-04-27). It confirms one free machine account in addition to a personal account and requires human account creation. This excludes a plan that automatically creates dozens of free pseudo-human GitHub accounts. GitHub Apps remain the proposed automation route; a native app author must be read back rather than inferred from an email.
